# Swift Lotto 🎱

> 기존 [Java 로또 게임 미션](https://github.com/JohnPrk/java-lotto-8)을 **Swift와 iOS 환경**으로 마이그레이션한 프로젝트입니다

<br>
<br>

## 🎯 미션 목표와 한계(기술 부채)

### 1-1. 프로젝트의 핵심 목표

이 프로젝트의 핵심 목표는 서버 개발자로서 익숙한 Java/Spring 환경을 벗어나, 클라이언트(iOS) 개발의 패러다임과 Swift 언어의 특성을 깊이 있게 학습하는 것입니다.

즉, “같은 로또 게임을 다른 언어로 한 번 더 구현해보는 것”이 아니라, 서버에서 요청/응답 및 콘솔을 다루던 사고방식이 iOS 앱의 이벤트/상태/화면 전환 환경에서는 어떻게 바뀌는지를 경험해보는 것을 목표로 했습니다.

<br>

### 1-2. Swift 철학을 iOS 앱으로 직접 만들어보기
Swift를 단순히 “새로운 문법을 익힌 언어”로 끝내고 싶지 않았습니다. 

이 언어가 **어떤 철학을 가지고 설계되었는지**, 그리고 그 철학이 **실제 앱 개발 과정에서 어떻게 드러나는지**를 직접 경험하는 것을 목표로 했습니다.

<br>

### 1-3. ‘꼬리 질문’을 통한 단계적 고도화

이 프로젝트는 처음부터 완성된 기획에서 시작된 것이 아니라, **“큰 주제”에서 출발해 계속 꼬리를 무는 질문들로 구현을 확장**시켰습니다.

#### **큰(시작) 주제**

	 “Java 로또 미션을 Swift/iOS로 옮겨보자.”

#### **1차 꼬리 질문 – UI와 오토레이아웃**

	 ❓ "Java의 `System.out.println` 대신, 아이폰 화면에는 어떻게 글자를 띄울까?"

                                 ⬇️

	✅ Storyboard와 AutoLayout(Constraints)을 사용해, 로또 화면을 구성해보자!

#### **2차 꼬리 질문 – MVC에서 MVVM으로**

	 ❓ "MVC 패턴으로 시작했는데, 화면 로직과 비즈니스 로직이 `ViewController` 안에 섞이면서 비대해지는 것은 괜찮은 걸까?"
	 
	                                  ⬇️
									  
	 ✅ `ViewModel`을 도입하고 입력 파싱, 계산 및 출력 기능을 분리하고, 
	    클로저 기반으로 `view(controller)` ↔ `ViewModel` 간 단방향 데이터 흐름을 만드는 MVVM 아키텍처 적용해보자!

#### **3차 꼬리 질문 – 실제 회차 데이터와 크롤링(미션 기한이 1주 연장)**

	❓ "어차피 로또라면, 내가 직접 입력한 당첨 번호만 쓰지 말고 진짜 동행복권 회차 데이터를 가져와서 결과를 비교해볼 수는 없을까?"
	
		                                  ⬇️
										  
	✅ `LottoCrawler`를 만들어 동행복권 사이트를 크롤링하고, 실제 회차별 당첨 번호/보너스/당첨금 정보를 기반으로 번호를 맞춰보자!

### 2. 한계와 기술 부채 (Limitations & Technical Debt)

이번 프로젝트는 제한된 시간과 범위 내에서 iOS/Swift 학습을 우선순위로 두고 진행했기 때문에, 의도적으로 뒤로 미루거나 다루지 않은 부분들이 있습니다. 이들은 이후 단계에서 해야 할 기술 부채(Technical Debt)로 남겨두었습니다.


#### **1. AI 활용을 통한 '선 구현, 후 분석' 방식**
* Swift 문법과 UIKit 프레임워크의 방대한 내용을 단기간에 모두 체득하고 구현하기에는 물리적인 시간이 부족했습니다.
* 따라서 **AI 툴을 활용해 기능 동작 코드를 우선 생성하고, 이후 코드를 역으로 분석하며 문법과 구조를 이해하는 방식**을 택했습니다.
* 결과적으로 기능 구현은 완료했으나, 공식 문서를 기반으로 한 깊이 있는 원리 이해보다는 실용적인 구현에 비중을 두었습니다.

#### **2. 테스트(TDD) 대비 UI/Layout 구현 우선**
* 기존에는 TDD 기반의 단위 테스트를 우선시했으나, 이번 프로젝트에서는 UIKit 기반 UI 구현과 레이아웃 작업에 집중했습니다.
* AutoLayout 제약 조건 설정, Storyboard와 코드 간 연결, Safe Area 대응 등 시각적 요소에 많은 시간을 할애한 관계로 단위 테스트 및 UI 테스트 작성은 현재 생략된 상태입니다.

#### **3. 외부 데이터 연동과 도메인 객체 활용의 타협**
* 초기 설계 단계에서 Java 기반의 엄격한 도메인 객체(Lotto, WinningLotto, BonusNumber 등)와 유효성 검사를 잘 구현했으나, 실제 회차 조회 기능(HTML 크롤링)을 추가하는 과정에서 외부 데이터 형식이 기존 도메인 모델과 정확히 일치하지 않아 일부 로직을 객체화하지 못하고 외부(controller 혹은 viewModel)에 유효성 검증 및 출력 작업들이 섞여있습니다.

## 🚀 주요 기능 및 구현 내용

### 1. 도메인 설계 (Domain Modeling)
* **Java 로직의 Swift 이식**: `Lotto`, `WinningLotto`, `BonusNumber` 등 핵심 도메인 객체를 구조체(struct)로 구현하고, 생성자 시점에 유효성 검사(Validation)를 강제하여 데이터 무결성을 확보했습니다.
* **객체 지향적 설계**: 로또 번호 생성, 매칭 로직, 수익률 계산 등의 책임을 각 도메인 객체에 적절히 분배하여 응집도를 높였습니다.
<br>

### 2. UI 및 레이아웃 (User Interface)
* **콘솔 로직의 시각화**: 텍스트 입출력으로 진행되던 콘솔 게임의 흐름(Flow)을 그대로 유지하면서, 이를 `Storyboard`와 `Constraints`를 활용해 모바일 UI로 직관적으로 구현했습니다.
* **스크롤 기반 뷰 구성**: `UIScrollView` 내부에 콘텐츠를 배치하여, 작은 화면에서도 입력 폼과 결과 리스트를 유연하게 확인할 수 있도록 설계했습니다.
<br>

### 3. 아키텍처 (MVC → MVVM)
* **ViewModel 분리**: 기존 `ViewController`에 집중되어 있던 비즈니스 로직을 `ViewModel`로 이관하여 뷰 컨트롤러의 역할을 'UI 업데이트'로 한정지었습니다.
* **단방향 데이터 바인딩**: 클로저(Closure)와 `[weak self]`를 활용해 ViewModel의 데이터 변화를 View가 즉시 감지하고 업데이트하는 반응형 구조를 구축했습니다.
<br>

### 4. 실시간 크롤링 (Web Crawling)
* **비동기 데이터 수집**: `async/await`와 `URLSession`을 활용해 메인 스레드 차단(Freezing) 없이 동행복권 웹사이트의 데이터를 백그라운드에서 수집합니다.
* **정밀 파싱 로직**: `EUC-KR` 인코딩 호환성 문제를 해결하고, `NSRegularExpression`(정규식)을 적용해 HTML 태그 사이의 핵심 데이터(번호, 당첨금 등)만 정확히 추출합니다.
